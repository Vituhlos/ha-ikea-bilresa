# v0.6.0 release-readiness checklist

Working checklist for cutting a stable **v0.6.0**. `PROJECT_STATUS.md` remains the
canonical, dated validation record; this file only orders the outstanding work and
marks what blocks the stable tag. Keep the validation vocabulary
(Implemented / Static / Unit / CI / Hardware / Released) — never infer Hardware
from CI.

**Current state (2026-07-18):** highest tag is the prerelease `v0.6.0-rc.6`
(commit `dd14521`, CI green, deployed). No stable `v0.6.0`. `origin/main` is still
at `f1e7583`; PR #2 (`agent/dual-button-0.6`) and PR #1 (`agent/stabilize-0.5-x`)
are both open. The BILRESA **dual button (E2489)** feature (B0–B4) is implemented

(HW) needs the physical device (owner) · (code) implementable without hardware.

## 🔴 Blockers — required before tagging a stable v0.6.0

- [ ] **1. Scroll smoothing on large cumulative batches** (code done, **HW A/B
  outstanding**). Mechanism implemented 2026-07-29: a single notch (eager first
  notch, hold-to-ramp step) is never smoothed, and a batch is spread in
  proportion to its size up to the binding's configured value. The `Transition`
  field became `Smoothing of large jumps` and is that ceiling, so the A/B runs
  from the UI without a new release. **The duration itself is still unmeasured**
  — per `PROJECT_STATUS.md` no value is accepted without a controlled Hardware
  A/B, so this item stays open until one is recorded.
  The second half of the original symptom — the light looking stationary at
  min/max — is **not** a smoothing defect and is deliberately not addressed
  here: the suppressed service calls are correct, since the target really is at
  its limit. If it needs anything, it needs feedback elsewhere in the UI.
- [ ] **2. Hardware-verify the RC.6 target-preservation fix** (HW).
  "Keep the calculated target authoritative through delayed state echoes" is
  Implemented + CI + deployed but recorded as **Not corrective Hardware**. Needs a
  new controlled gesture to confirm on the physical wheel.
- [ ] **3. Close Section G (physical scroll optimization)** (HW).
  Recorded as in progress with no G Hardware box claimed yet.
- [ ] **4. B3 panel — real Home Assistant pass** (HW/owner).
  Light / dark / one custom theme visual review, plus keyboard + screen-reader
  pass for the dual-button view. Only browser-harness evidence exists so far.
- [ ] **5. Release mechanics** (owner + agent).
  Cut a **stable** (non-prerelease) tag from a CI-green commit and merge the PR
  chain: PR #2 → `agent/stabilize-0.5-x`, then PR #1 → `main`. Today `main` has
  none of this. **Directly wanted by a real external user** — see issue #3
  (double-press in the UI): that feature already exists in the pre-releases and
  only a stable release ships it to users on the default channel (latest stable is
  `v0.5.0`, which predates it).

## 🟡 Investigate — quality, may or may not block

- [x] **6. RC.5 brightness accounting anomaly** (code/analysis). **Real bug, fixed
  in the working tree on 2026-07-29 — not CI-verified, not Hardware-verified.**
  Not clamping and not rounding: a delayed absolute state echo landing in the gap
  *between* two Matter gestures of one physical rotation rebased the next notch
  from state that was still catching up. RC.6 only protected the inside of a
  gesture. The calculated target now survives that gap, and a report is only
  accepted as our own echo when its value matches a recently dispatched target.
  Full diagnosis, arithmetic and risks in `PROJECT_STATUS.md`. **Confirm on the
  physical wheel together with #2** — the same controlled gesture covers both.
- [ ] **7. Verify the dual-button icon renders** (owner, visual).
  Confirm `bilresa:dual-button` actually resolves on the button entity / panel in
  the deployed build.
